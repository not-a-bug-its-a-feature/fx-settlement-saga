# [WIP] 資金移動・精算 Saga 実験リポジトリ

マルチ通貨の送金・振替やポイント・クレジット精算の流れで、**途中の失敗、重複したリクエストや処理、処理漏れ**をどう防ぐか試すための Go プロジェクトです。

## 1. なぜ作ったか
残高の仮押さえから為替・送金・精算へつながる非同期の処理では、こういう問題が起きやすい
- 通信の再送や重複通知による**二重引き落とし・二重反映・二重の戻し処理**
- 途中で失敗したときの**戻し処理（仮押さえ解除など）の漏れや順番ズレ**
- ワーカーやキューの不調で**途中の状態のまま止まってしまうこと**

**Saga の状態管理と Outbox・Inbox、さらに漏れ検知バッチ**を組み合わせて、処理が最後まで結果整合性と復旧のしやすさを確かめる。

## 2. 状態の動き
- **正常な流れ:** `INITIATED` → `SOURCE_HELD` →（`FX_LOCKED`）→ `SETTLED`
- **戻す流れ:** `SOURCE_HELD` / `FX_LOCKED` → `COMPENSATING` → `CANCELLED`（残高の仮押さえ解除や原状回復）
- **手動確認（切り分け）:** `MANUAL_REVIEW`（再試行の上限を超えたときや状態がおかしいときは止めて、ログや通知へ出す）

## 3. 整合性と復旧の仕組み
- **重複防止:** リクエストのキーやイベント ID を `Inbox` で管理しつつ、許された状態の変化だけ通すようにする
- **Outbox パターン:** 状態の変更とイベントの保存を同じ DB トランザクションで確定してから、あとで非同期で送る
- **順番の整理:** 送金 ID や対象口座ごとに分けて基本の順番を揃えつつ、順番が前後したり重複したりしても壊れないようにする
- **漏れ検知バッチ:** ずっと途中の状態のまま残っているものを定期的に見つけて、再送や再試行をするか `MANUAL_REVIEW` に回す

## 4. フォルダ構成
- `cmd/api`: 送金・精算リクエストの受付と状態確認のサーバー
- `cmd/worker`: イベント処理、Saga の各ステップや戻し処理、Outbox 送信
- `cmd/sweeper`: 止まっている処理や漏れている処理を探して直したり切り分けたりするバッチ
- `internal/domain`: 台帳や残高押さえのモデルと状態変化のルール
- `internal/saga`: 全体の流れと戻し処理の制御
- `internal/outbox`, `internal/inbox`: Outbox と Inbox の仕組み
- `internal/infra`: DB、Redis、Kafka（またはローカル用の仮実装）
